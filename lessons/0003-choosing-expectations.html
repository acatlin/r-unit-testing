Choosing the right expectation

So far every check has been expect_equal(). testthat has a few dozen expectations, and you need about ten of them. Picking the specific one gets you a failure message that tells you what went wrong.

Test a function that returns a data frame: its values, its column names and its type, each with the expectation built for the job.

From last time

  1. How does testthat recognise a test file inside tests/testthat/?

    • Its name starts with test-.
    • Its name ends with -test.
    • It contains a test_that() call.
    • It sits next to run-tests.R.

    Only the file name counts: test- at the start and .R at the end.

  2. Which ordering runs from the smallest unit to the largest?

    • Expectation, test, file.
    • Test, expectation, file.
    • File, test, expectation.
    • Expectation, file, test.

    Expectations are grouped into tests, and tests are organised in files.

Why not expect_true() for everything?

You could write any check as a logical condition wrapped in expect_true(). Compare what each version tells you when the check fails. Both tests below wrongly claim that rescale01(1:3) has four elements.

The first says only that something was not true. The second tells you the length was 3, which is what you need to start fixing it. The testthat documentation calls expect_true() and expect_false() “fall-back expectations that you can use when none of the other more specific expectations apply.”

testthat reference, logical expectations: “The disadvantage is that you may get a less informative error message.”

Testing a function that returns a data frame

Most of your functions take a data frame and return one. Here is a small dplyr wrapper from R/clean.R that counts rows and averages a column within groups.

The recipe has three parts, and it works for nearly any data-frame function. Arrange a tiny input by hand. Act by calling the function. Assert by comparing with an expected result that you also typed by hand.

Three rows are enough. You can check the answer in your head (two people in “a” averaging 15, one in “b” at 60), and if the test fails the difference is small enough to read. Had you typed the mean for “b” as 50, the report would be:

testthat points at the column (mean) and the row (2) that disagree, which is why it pays to compare whole tibbles with expect_equal() when they are small.

Common trap

Never build the expected value by calling the function you are testing. expect_equal(summarise_by(staff, dept, pay), summarise_by(staff, dept, pay)) passes no matter how broken the function is. The expected side must come from somewhere else: your own arithmetic.

Structure checks

Sometimes you care less about exact values and more about the shape of the result: it is a tibble, and it has the documented columns. Those get a test of their own.

Notice that staff is built again inside this test. Each test makes everything it needs, so you can read, run or move it without looking anywhere else.

“A test should ideally be self-sufficient and self-contained.” R Packages (2e), ch. 14, “Designing your test suite”.

Try it

  1. Add both summarise_by() tests to your test-clean.R and run source("run-tests.R"). You need the tibble package installed.
  2. In the expected tibble, change n = c(2L, 1L) to n = c(2, 1) (doubles instead of integers). Does expect_equal() still pass? Now swap in expect_identical() and read the message.
  3. Write a new test for rescale01() with three expectations: the result is of type "double", has the same length as the input, and its largest value is at most 1.

Check yourself

  1. Why prefer expect_length(x, 3) to expect_true(length(x) == 3)?

    • Its failure message shows the real length.
    • It runs faster on very long vectors.
    • It additionally checks the type of x.
    • It is the only form testthat accepts.

    Both work. The specific expectation tells you what the length actually was; expect_true() can only say “not TRUE”.

  2. A function returns integer counts. Your hand-typed expected tibble has n = c(2, 1), which are doubles. What happens?

    • expect_equal() passes but expect_identical() fails.
    • expect_equal() fails but expect_identical() passes.
    • expect_equal() and expect_identical() both pass.
    • expect_equal() and expect_identical() both fail.

    expect_equal() treats 2 and 2L as equal. expect_identical() also compares types, and reports that one column is integer and the other double.

  3. You want to check that a result has exactly the columns dept, n and mean. Which expectation is the most direct?

    • expect_named()
    • expect_length()
    • expect_type()
    • expect_match()

    expect_named(out, c("dept", "n", "mean")). expect_length() would confirm there are three columns but not which ones.

  4. What does expect_type(rescale01(1:3), "integer") do?

    • Fails, because division returns a double.
    • Passes, because the input was integer.
    • Fails, because types cannot be tested.
    • Passes, because doubles count as integers.

    rescale01() divides, and division in R always gives a double. The message reads: Expected `rescale01(1:3)` to have type "integer". Actual type: "double".

  5. Where should the expected value in a summarise_by() test come from?

    • A small expected tibble typed by hand.
    • One more call to the same function.
    • A random sample of the production data.
    • The full dataset with thousands of rows.

    The expected value has to be independent of the code under test and small enough to verify by eye.
