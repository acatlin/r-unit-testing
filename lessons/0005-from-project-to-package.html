From project to package

Your project already has an R/ folder and a tests/testthat/ folder. That is most of an R package. Taking the last step gets you tooling that loads your code, runs your tests and checks your work with one keystroke each.

By the end you can

Move your functions and tests into a package and run all of them with devtools::test().

From last time

  1. Beyond “an error occurred”, what does expect_error(f(x), "must be numeric") check?

    • That the message matches that text.
    • That the error has that class.
    • That the function returns that text.
    • That the warning matches that text.

    The second argument is a regular expression matched against the error message.

  2. After finding a bug, why write the failing test before the fix?

    • It proves the test detects the bug.
    • It makes the fix run more quickly.
    • It hides the bug from other users.
    • It removes the need for a fix.

    A test you have seen fail is one you know is able to fail.

Build it

You need two more packages, both installed once: install.packages(c("devtools", "usethis")). Then follow the steps. Each usethis function creates files and tells you what it did.

  1. Create the package. Run this from a folder that is not inside another project. It makes a new folder called cleaner and opens it.
  2. Add a file for your functions, and paste in the four functions from your project's R/clean.R.
  3. Switch on testing. The 3 is the edition.
  4. Add a test file, and paste in your tests without the local_edition(3) line. Delete the placeholder test that usethis put there.
  5. Declare the packages you depend on. summarise_by() uses dplyr; the tests use tibble.
  6. Run the tests.
use_testthat() “initializes the unit testing machinery for your package”; use_test() “opens and/or creates a test file”. R Packages (2e), ch. 1, “The Whole Game”.

What you now have

cleaner/
├── DESCRIPTION              settings: name, dependencies, testthat edition
├── NAMESPACE                managed for you
├── R/
│   └── clean.R              your functions
└── tests/
    ├── testthat.R           runs the tests during a full package check
    └── testthat/
        └── test-clean.R     your tests

Compare this with the tree in Lesson 2. R/ and tests/testthat/ are exactly where they were. run-tests.R is gone, and two things have appeared.

DESCRIPTION holds the package's settings. Open it and you will find the line that replaces every local_edition(3):

“The usual way to activate the 3rd edition is to add a line to your DESCRIPTION… This will activate the 3rd edition for every test in your package.” testthat 3e.

tests/testthat.R is a three-line launcher used when the whole package is checked. Leave it alone; R Packages says plainly, “Do not edit tests/testthat.R!”

Common trap

In a script you write library(dplyr) at the top. In package code under R/, don't. Call other packages' functions as dplyr::group_by() and declare the package with usethis::use_package("dplyr"). The functions in this course were written that way from the start, so they move over unchanged.

“Our recommended default is to call external functions using the package::function() syntax.” R Packages (2e), ch. 11.

The working loop

With a package, day-to-day work becomes a short cycle. You will repeat it many times an hour.

StepCommandRStudio shortcut
Edit a function or a test
Reload your functions to try them in the consoledevtools::load_all()Ctrl/Cmd + Shift + L
Run every testdevtools::test()Ctrl/Cmd + Shift + T
Now and then, check the whole packagedevtools::check()Ctrl/Cmd + Shift + E
Shortcuts as given in R Packages, ch. 13 and ch. 1.

Because running the tests is now one keystroke, you will run them far more often, and tests that are run often are the ones that catch things.

Try it

  1. Follow the six steps under “Build it” with your own project from Lesson 4. Finish with PASS 17 or more. A finished copy is in examples/cleaner.
  2. Break clean_names() on purpose (delete the tolower() line), press the test shortcut, and read the report. Undo the change and run again.
  3. Add a new function to the package using the full loop: use_r(), use_test(), write a failing test first, then make it pass. An idea: squish(), which trims a string and collapses runs of spaces into one.

Check yourself

  1. In a package, what replaces local_edition(3) at the top of each test file?

    • An edition field inside DESCRIPTION.
    • A library(testthat) line in NAMESPACE.
    • A source() call in testthat.R.
    • An options() call in .Rprofile.

    Config/testthat/edition: 3 in DESCRIPTION sets the edition for every test in the package.

  2. Which call creates tests/testthat/ and sets the edition for a package?

    • usethis::use_testthat(3)
    • usethis::use_test("clean")
    • devtools::load_all()
    • devtools::check()

    use_testthat(3) is run once per package. use_test() is run once per test file.

  3. Why do package tests need no source("R/clean.R")?

    • devtools::test() loads the package code first.
    • Package tests never call your functions.
    • testthat.R sources each file by name.
    • R sources every folder at startup.

    devtools::test() loads everything under R/ before it runs the tests, so your functions are already available.

  4. Which file does usethis::use_test("clean") create?

    • tests/testthat/test-clean.R
    • tests/testthat/clean-test.R
    • tests/testthat/check-clean.R
    • tests/test-clean/testthat.R

    It adds the test- prefix and puts the file in tests/testthat/, matching R/clean.R.

  5. How should package code in R/clean.R use dplyr's group_by()?

    • Write dplyr::group_by() and list dplyr in Imports.
    • Call library(dplyr) at the top of clean.R.
    • Call install.packages("dplyr") at the top of clean.R.
    • Copy the group_by() source code into clean.R.

    Use the package::function() form, and let usethis::use_package("dplyr") add dplyr to Imports in DESCRIPTION.

Where to go from here

You can now write, organise and run tests by hand, in a project or a package. There is more to learn, and later lessons in this course will take it up: snapshot tests for output that is awkward to type out, test fixtures and helper files, skipping tests, and measuring how much of your code the tests reach.

Testing is also a craft that people argue about. When you have a question with no clear answer in the documentation, such as how much testing is enough for an analysis project, ask people who do this for a living. The Posit Community forum has a package-development category that covers “devtools, roxygen2, testthat, and friends”.

Read next (primary source)

Ask. Package setup produces unfamiliar messages the first time. Copy the message and take it to your instructor, a classmate, or an AI assistant before you spend half an hour guessing.
