test_that() and test files

An expectation typed at the console is gone when you close R. This lesson gives your expectations a name, a file, and one command that runs all of them.

By the end you can

Lay out an R project with a tests/testthat/ folder, run every test with one line, and read the report.

From last time

Two questions from Lesson 1. Answer before reading on; recalling is what makes it stick.

  1. What does a passing expect_equal() print at the console?

    • Nothing at all.
    • The word TRUE.
    • A green tick.
    • The compared values.

    Expectations are silent when they pass.

  2. Which expectation demands an exact match, with no numeric tolerance?

    • expect_identical()
    • expect_equal()
    • expect_same()
    • expect_exact()

    expect_equal() tolerates tiny floating-point differences; expect_identical() does not. The other two do not exist.

Group expectations into a test

A test is a call to test_that(). It takes a description and a block of code in braces that holds one or more expectations about a single behaviour.

Write the description so that it completes the sentence “Test that…”. When a test fails months from now, that sentence is the first thing you will read, so make it say what the function should do, not just the function's name.

“Names should be brief, but evocative. It's common to write the description so that it reads like a natural sentence.” test_that() reference. The emoji is chosen at random.

Give tests a home

Tests live in their own files, apart from the code they test. The layout below is the one testthat expects, and the one R packages use, so learning it now saves relearning it later.

cleaning-project/
├── R/
│   └── clean.R              your functions
├── tests/
│   └── testthat/
│       └── test-clean.R     tests for the functions in clean.R
└── run-tests.R              three lines that run everything

Two rules matter. Test files go in tests/testthat/, and their names start with test- and end with .R. A file called clean-tests.R is not treated as a test file. If other test files sit beside it, testthat runs those and skips it without a word.

Test files “start with either test- or test_, and end with .r or .R.” testthat, “Special files”. The convention R/clean.R ↔ test-clean.R is from R Packages, ch. 13.

The three levels have names you will see in every testthat document:

Tests are organised hierarchically: expectations are grouped into tests which are organised in files.
Wickham & Bryan, R Packages (2e), ch. 13

What is local_edition(3)?

testthat has a current “third edition” with clearer failure messages and stricter comparisons. Packages switch it on in a settings file. A plain project has no such file, so each test file switches it on in its first line. Treat it as a line you always type; it disappears again in Lesson 5.

“local_edition() allows you to temporarily (within a single test or a single test file) change the active edition of testthat.” reference; background in “testthat 3e”.

Run everything

The test file calls rescale01() but does not define it. In a plain project, loading your functions is your job. run-tests.R does it and then hands the folder to testthat.

With test_dir() outside a package, “you are responsible for ensuring that the functions to test are available”. test_dir() reference.

Each row is one test file (“clean” is test-clean.R without its prefix and suffix). The columns count Failures, Warnings, Skips and passes. Note what is being counted: 6 is the number of expectations, not the number of tests (3) or files (1).

Common trap

If every test fails with could not find function "rescale01", nothing is wrong with your tests. The functions were never loaded: you ran test_dir() without first running source("R/clean.R").

Try it

  1. Download the starter project (or build the three files above by hand; typing them is good practice). You need the dplyr package installed, because one helper in clean.R uses it.
  2. Open the project folder in RStudio or Positron so that it is your working directory, then run source("run-tests.R"). You should see PASS 6.
  3. Add a third expectation to the parse_money() test, for the input "$3,000". Run again and watch the count become 7.
  4. Rename the file to clean-tests.R and run again. You should get the error No test files found. Rename it back.

Check yourself

  1. What is the first argument of test_that()?

    • A sentence describing what should happen.
    • The folder containing the test files.
    • The function whose output is checked.
    • The number of expectations to run.

    test_that(desc, code): a description, then a braced block of expectations.

  2. Which of these files in tests/testthat/ will test_dir() run?

    • test-clean.R
    • clean-test.R
    • check-clean.R
    • clean.R

    Test file names must start with test- (or test_). Anything else is silently skipped.

  3. You run test_dir() and every test reports could not find function "rescale01". What is the likeliest cause?

    • The file defining it was never sourced.
    • The test file has the wrong name.
    • The testthat package is not installed yet.
    • The expected values were typed in wrong.

    In a plain project you must source() your functions before running the tests. A misnamed test file would not run at all, so it could not produce this error.

  4. A run ends with [ FAIL 1 | WARN 0 | SKIP 0 | PASS 5 ]. What happened?

    • Five expectations passed and one failed.
    • Five files passed and one failed.
    • Five functions passed and one failed.
    • Five tests passed and one skipped.

    The summary counts expectations. Those six expectations might sit in three tests in one file.

  5. Why does a test file in a plain project begin with local_edition(3)?

    • It switches on testthat's third edition.
    • It loads the functions under test.
    • It repeats every test three times.
    • It limits output to three failures.

    It selects testthat's third edition for that file. Loading your functions is the job of source().

Stuck or curious?

Ask. If a run does not look like the ones on this page, copy the whole report and take it to your instructor, a classmate, or an AI assistant. “Here is what I ran, here is what I got, here is what I expected” is the most useful question format there is.
