Your first expectation

You already test your code. You run a function in the console, look at what comes back, and decide whether it seems right. This lesson turns that glance into one line of R that can be run again tomorrow.

By the end you can

Write an expect_equal() call for a function of your own, and read what testthat says when it passes and when it fails.

The check that disappears

Here is a small helper of the kind you write all the time while cleaning data. It rescales a numeric column so that its smallest value becomes 0 and its largest becomes 1.

That looks right, and you move on. The trouble is that the check lived only in your head. Next month you change rescale01(), or a classmate does, and nobody repeats it. A unit test is the same check written down as code, so the computer can repeat it for you after every change.

Hadley Wickham and Jennifer Bryan list four ways this pays off: you have fewer bugs because you are explicit about how code should behave; code that is easy to test tends to be better structured; a failing test tells you where to start work; and you can make big changes without worrying about breaking something by accident.

Source: R Packages (2e), ch. 13, “Testing basics”.

Say what you expect

The package that nearly everyone uses for this in R is testthat. Install it once, then load it.

Its basic building block is the expectation: a function whose name starts with expect_ and that compares what your code did with what you say it should have done. The one you will use most is expect_equal().

Run it, and nothing is printed. Silence means the expectation passed. Read the call as a sentence: “I expect rescale01(c(0, 5, 10)) to equal c(0, 0.5, 1).”

PositionNameWhat you put there
FirstactualA call to your function. R runs it.
SecondexpectedThe right answer, which you work out yourself and type in.
Signature: expect_equal(object, expected, ...). See testthat reference, equality expectations.

Equal is not the same as identical

Computers store most decimal numbers approximately, which leads to a famous surprise.

If expectations compared numbers with ==, tests of numeric code would fail for reasons that have nothing to do with bugs. So expect_equal() ignores tiny floating-point differences (anything smaller than roughly 1.5 × 10−8 in relative terms). Its strict sibling, expect_identical(), does not.

“expect_equal() checks for equality, with some reasonable amount of numeric tolerance… If you want to test for exact equivalence, use expect_identical().” R Packages, ch. 13.

For the numeric results that fill data science work, reach for expect_equal() first.

Try it

Open R and do these in the console. Work out each expected value in your head or on paper before you run anything; that is the whole point.

  1. Define rescale01() from the top of this page and load testthat.
  2. Write an expectation for rescale01(c(-2, 0, 2)). It should be silent.
  3. Write one for rescale01(c(10, 20, 30, 50)). If it fails, read the message and decide who is wrong: the function, or your arithmetic.
  4. Break one of your expectations on purpose, read the failure, and repair it.

Check yourself

Answer from memory, without scrolling up. Getting one wrong and reading why is worth more than getting it right by looking.

  1. You run an expectation at the console and R prints nothing at all. What happened?

    • The expectation passed without complaint.
    • The expectation was skipped entirely.
    • The expectation failed without output.
    • The expectation never actually ran.

    A passing expectation is silent. Only a failure prints anything.

  2. In expect_equal(rescale01(c(0, 5, 10)), c(0, 0.5, 1)), what is the second argument?

    • The right answer, which you supplied yourself.
    • The value your function has actually returned.
    • The biggest numeric gap testthat will allow.
    • The message printed when the check fails.

    The first argument is the actual result (a call to your function). The second is the expected result, which comes from you.

  3. Why does expect_equal(0.1 + 0.2, 0.3) pass even though 0.1 + 0.2 == 0.3 is FALSE?

    • It ignores very tiny differences by default.
    • It rounds both values to two decimals.
    • It converts both values into character strings.
    • It only compares the types of values.

    expect_equal() has a small numeric tolerance. expect_identical() has none, so it fails here.

  4. What does writing a check as an expectation give you that looking at console output does not?

    • It can be rerun after every change.
    • It makes the function run noticeably faster.
    • It removes any need for reading documentation.
    • It guarantees the function has no bugs.

    A written check is repeatable. It makes bugs less likely, not impossible: a test only covers the cases you thought to write.
