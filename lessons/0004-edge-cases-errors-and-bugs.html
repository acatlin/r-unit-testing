Edge cases, errors and bugs

Every test so far fed a function tidy input and checked a tidy answer. Real data is not tidy. This lesson is about the inputs that break things, and a habit that keeps a bug from coming back once you have fixed it.

By the end you can

Find a real bug in rescale01(), pin it down with a failing test, fix it, and watch the test go green.

    expect_s3_class(out, "tbl_df"). expect_type() looks at the base type, which for any data frame is "list".

    • Their definitions must be sourced.
    • Their names must start test-.
    • Their package must be installed.

Ask what could go wrong

The tests you have written cover the happy path: ordinary input, ordinary output. Bugs mostly live elsewhere. For a function that takes a column of data, run through this list and ask of each item, “what should happen?”

A bug, caught test-first

Now the second item on the list. What does rescale01() do with a column where every value is the same?

The range is zero, so the function divides zero by zero. One constant column would quietly fill a model matrix with NaN. That is a bug. The tempting move is to fix it straight away. Do this instead:

Always write a test when you discover a bug.
Wickham & Bryan, R Packages (2e), ch. 14

Step 1: write the test and watch it fail

Decide what should happen (all zeros is a sensible answer) and say so.

The failure matters. It proves that the test can see this bug. A test written after the fix passes the first time you run it, and you never find out whether it would have caught anything.

Step 2: fix the function

Step 3: run everything again

Run all the tests, not just the new one. The new test should pass, and so should every old one. The old ones are how you know the fix did not break something else.

This fail-first rhythm is often called “red, green”. R Packages: “When we start to fix a bug, we first like to convert it into a (failing) test.” ch. 13.

That also passes. could not find function "rescale1" is an error, and a bare expect_error() is satisfied by any error at all. A test like this can stay green for years while testing nothing.

Give expect_error() a second argument: a piece of text (a regular expression) that the error message must match.

Warnings

parse_money("n/a") returns NA with R's warning “NAs introduced by coercion”. If that is the behaviour you want, say so with expect_warning(). To state that well-formed input is quiet, use expect_no_warning().

A warning that no expectation asked for does not fail the test, but it is not hidden either: it is counted in the W column and in WARN on the summary line. Treat a nonzero WARN as something to investigate.

expect_no_warning() and friends “assert the absence of an error, warning, or message”.

One behaviour per test

Your test file now has several short tests for rescale01() rather than one long one. Keep it that way. When the constant-column test fails, its description tells you what broke before you read a line of code.

“Strive to test each behaviour in one and only one test.” R Packages (2e), ch. 14.

Check yourself

  1. A test contains expect_error(rescale1("a")), where the function name is a typo. What happens when it runs?

    • It passes, since any error satisfies it.
    • It fails, since the function is missing.
    • It is skipped, since nothing was called.
    • It warns, since the name looks wrong.

    “Could not find function” is itself an error, and expect_error() with one argument accepts any error.

  2. How do you make sure expect_error() saw the error you intended?

    • Supply text that the message must match.
    • Wrap the call inside another test_that() block.
    • Call the function twice in one expectation.
    • Use expect_true() around the same call instead.

    The second argument is a regular expression matched against the error message, as in expect_error(rescale01("a"), "must be numeric").

  3. You discover that rescale01(c(5, 5, 5)) returns NaN. What is the best first move?

    • Write a new test that reproduces it.
    • Fix the function before you forget how.
    • Delete the tests that still pass now.
    • Note it in a comment for later.

    A test that fails first proves it can detect the bug, and stays behind to stop the bug returning.

  4. Which set of inputs covers the usual edge cases for a numeric helper?

    • Missing values, identical values, and wrong types.
    • Three ordinary numeric vectors of different lengths.
    • The same typical vector, run three times.
    • Whatever values appeared in the last dataset.

    Edge cases sit at the boundaries of what the function was written for. More ordinary input mostly re-tests the happy path.

  5. A test calls parse_money("n/a") without using expect_warning(). What does the run report?

    • A warning, counted in the WARN column.
    • A failure, counted in the FAIL column.
    • A skip, counted in the SKIP column.
    • Nothing, since testthat ignores all R warnings.

    Unexpected warnings are reported and counted, but they do not make the test fail.
